# 대출신청 암호화·토큰 설계 — 시범 MVP

수정일: 2026-10-16. 이 문서는 현재 MVP 설계와 구현 현황의 기준이다.
현재 계약은 Mustsem(chainId 7601, MST)에 배포한 v2 Manager 0x6D1004CB292e3ec45A4c4A0834C0eedAAbe16E38이다.
v2는 역할별로 여러 주소를 등록하고, 신청마다 서버가 고른 담당 평가사·은행을 온체인에 고정한다.
배포 거래·생성자 인자·런타임 바이트코드·토큰 연결 검증은 blockchain/deployments/mustsem.json에 기록했다.
이전 단일 담당자 계약(평가사·은행 1명 고정)은 폐기했으며 서버는 v2(`contractVersion() == 2`)에만 연결한다.
Solidity 0.8.24 + EVM Paris를 유지한다. IPLOAN_ZERO_GAS_PRICE=0으로 정상 네트워크 수수료를 사용한다.
자동 검증과 배포 확인이 전체 수동 통합 테스트 완료를 뜻하지 않는다.
이전의 “신청 시 NFT+SBT 동시 발급·에스크로” 및 “플랫폼 서버 대리 발급” 설계는 폐기한다.
실제 자금·법적 채권·담보권을 만들지 않는 시범 구현이다.

## 1. 확정 범위

- 차주, 신청별 담당 평가사, 신청별 담당 은행/여신심사역이 각자 MetaMask로 자신의 거래를 실행한다.
- 신청 자산은 토큰이 아니라 Manager의 신청 기록(struct)이다. 같은 appKey에 평가·승인·상환 상태를 누적한다.
- 신청 거래: 신청 기록 생성 + 담당 평가사 고정 + 평가사 SBT 발급. 은행은 아직 배정하지 않고 NFT도 발급하지 않는다.
- 평가 확정 거래: 보고서 CID·해시·평가액 기록 + SBT 소각 + 70% 규칙 자동심사 + (통과 시) 담당 은행 고정을 한 거래로 처리한다.
- 최종 승인 거래: 담당 여신심사역에게 채권 NFT를 새로 발급한다. 여신심사역과 은행 수령 주소는 같다.
- 최종 거절에는 NFT가 없다. 상환은 은행이 확인한 가상의 기록만 추가한다.
- 플랫폼 발급 지갑, 서버 개인키, 서버 자동 거래, 에스크로, 회원가입, 실송금, 이자 계산, 만기·연체, NFT 매매는 제외한다.
- 평가 초안은 기존 시연용 생성 함수이며 실제 LLM·TCB·특허청 연동은 아니다.
- 평가 확정·최종 결정은 되돌리지 않는다. 재시연은 새 신청으로 한다.

## 2. 역할과 주소

| 역할 | 등록 | 권한 |
|---|---|---|
| 관리자 | DEFAULT_ADMIN_ROLE, 배포 지갑 0xcdfBfb91DE6a35f243c10c8a291B632A7F20156e | 차주·평가사·은행 주소 추가·회수(admin.html), 관리자 추가 |
| 차주 | BORROWER_ROLE, 여러 주소 | 신청 |
| 평가사 | EVALUATOR_ROLE, 여러 주소. 첫 주소는 생성자에서 등록 | 담당 신청의 평가 확정, 평가 중 원본 열람 |
| 은행·여신심사역 | BANK_ROLE, 여러 주소. 첫 주소는 생성자에서 등록 | 담당 신청의 최종 승인/거절·상환 기록, 승인 후 원본 열람 |

배정: 서버가 체인의 역할 보유자 중에서 평가사는 신청 접수 시, 은행은 70% 기준을 통과하는 평가보고서를 준비할 때 고른다.
IPLOAN_ASSIGNMENT_EVALUATOR / IPLOAN_ASSIGNMENT_BANK로 특정 주소를 지정할 수 있고, 비우면 임의 선택한다.
차주 본인은 담당자가 될 수 없고, 평가사는 같은 신청의 은행이 될 수 없다. 서버와 계약 모두 검사한다.
차주는 서버가 고른 평가사를, 평가사는 서버가 고른 은행을 거래 인자로 넣는다. 계약은 역할과 신청별 고정만 검증하므로
직접 호출로 다른 등록 주소를 넣는 것은 막지 못한다. 서버의 /sync가 배정 불일치를 거절하고 원본 열람을 막는다.
기록된 담당자는 바꿀 수 없다. 담당자의 역할을 회수하면 실행·원본 열람이 막히고 해당 신청은 더 진행할 수 없다.
관리자 권한도 grantRole로 다른 주소에 줄 수 있으며, 받은 주소는 기존 관리자와 같은 권한을 가진다(admin.html은 관리자 추가를 제공하지 않는다).
서명 키는 서버에 없으며, 배포·역할 변경을 포함한 MetaMask 승인은 사람이 직접 수행한다.
개인키·시드 문구는 공유하지 않는다. 공개 개발 키를 실제 네트워크 배포에 사용하지 않는다.

## 3. 저장 위치와 공개 정보

### 원부 PDF

1. 프론트가 multipart의 registryDocument 필드로 Flask에 PDF를 전송한다(최대 20 MiB).
2. 원부 대조를 먼저 수행한다. 현재 verify_registry는 mock이다.
3. 일치하면 파일마다 키 32바이트, salt 32바이트, IV 12바이트를 새로 생성한다.
4. docFileHash = 0x + SHA256(salt || 평문).
5. AES-256-GCM 암호문을 IV(12) || ciphertext || tag(16) 형식으로 만든다.
6. 회사 방식처럼 https://api.mustree.kr/upload 에 multipart file로 암호문을 올린다.
7. CID·해시·신청·기업 프로필을 DB에 저장한다. 키·salt는 SQLite에만 저장하고 공개 API·체인·tokenURI에는 넣지 않는다.
8. 브라우저가 차주 MetaMask 거래를 보낸다. 서버는 해당 계약의 상태를 읽어서 DB를 동기화한다.

대조 불일치(422)는 doc_verify/hashMatch=0 신청만 저장하고 암호화·업로드·토큰 발급은 하지 않는다.
IPFS 실패(502/504)는 성공 신청이나 프로필 변경으로 처리하지 않는다.
IPFS 저장 성공(201) 뒤 MetaMask를 취소하면 신청·프로필·CID는 이미 DB에 있다. 등록 재시도는 그 CID를 재사용한다.
“기업정보만 저장” 버튼은 없다. 신청 저장 성공 시 기업 프로필을 자동 생성/갱신한다.
프로필 선택은 인증이 아니며, 프로필 변경이 과거 신청의 기업정보 스냅샷을 바꾸지는 않는다.

### 평가보고서

평가사가 화면에서 평가액을 확인·수정하면 서버가 공개용 JSON 초안을 준비한다.
appKey, fileHash, appraisedValue, summary를 정렬한 canonical JSON UTF-8 바이트로 만들어
SHA256 해시와 IPFS CID를 저장한다. 같은 보고서는 재사용한다.
담당 평가사 MetaMask가 confirmEvaluation을 실행해야 실제 확정이다. 보고서 업로드 자체는 평가 확정이 아니다.
평가액이 70% 기준을 통과하면 보고서 준비 응답에 서버가 배정한 은행 주소(bankWallet)가 함께 온다. 미달이면 비어 있다.
이 JSON은 암호화하지 않는다. 가상 내용만 입력하고 실제 영업비밀·개인정보를 넣지 않는다.

### 공개 범위와 제한

- 체인에는 차주·담당 평가사·담당 은행 지갑, 원부 CID·salted hash, 신청금액, 보고서 CID·해시·평가액, 상태, 상환 합계가 공개된다.
- tokenURI는 원부 CID·fileHash·암호화 방식·상태·상환 합계를 제공한다. 두 토큰은 같은 신청의 암호문 CID를 참조한다.
- appKey는 keccak256(신청번호)이며 익명화를 보장하지 않는다.
- SBT가 있다고 IPFS가 비공개가 되는 것은 아니다. 암호문은 공개 가능하고 복호화 API를 서버가 제한한다.
- 키·salt를 가진 서버 운영자는 원본을 복호화할 수 있다. 종단간 암호화나 운영자 배제 설계는 아니다.
- API의 일반 신청 목록·기업 프로필·보고서 초안 준비는 MVP 공개 API다. 원본 열람과 온체인 변경만 지갑/계약 권한으로 제한한다.
- 원본을 한 번 다운로드한 평가사가 복사본을 보관하는 것은 SBT 소각으로 막을 수 없다.
- IPFS의 영구 보관·삭제·법적 권리·실금융 유효성은 보장하지 않는다. 외부 업로드 성공 뒤 DB 장애 시 고아 CID가 생길 수 있다.

## 4. 계약과 상태

OpenZeppelin 5.0.2, Solidity 0.8.24. IPLoanManager를 배포하면 생성자에서 두 토큰 계약도 생성한다.

| 계약 | 기능 |
|---|---|
| IPLoanManager | 역할, 신청 struct, 평가·자동심사·결정·상환 기록 |
| IPLoanAccessSBT | ERC-721 + ERC-5192 locked. Manager만 발급·소각. 전송·승인 불가 |
| IPLoanDebtNFT | 시연 채권 ERC-721. Manager만 발급. MVP에서는 은행 이후 전송 불가 |

| 상태 | 의미 | SBT | 채권 NFT |
|---|---|---|---|
| None(0) | IPFS/DB 준비, 아직 온체인 신청 없음 | 없음 | 없음 |
| Evaluating(1) | 차주 등록 완료, 평가 중(은행 미배정) | 담당 평가사 소유 | 없음 |
| Eligible(2) | 평가 확정, 70% 규칙 통과, 담당 은행 고정 | 소각 | 없음 |
| RuleRejected(3) | 평가 확정, 규칙 미통과(은행 없음) | 소각 | 없음 |
| Approved(4) | 은행 최종 승인 | 소각 | 은행 소유 |
| Rejected(5) | 은행 최종 거절 | 소각 | 없음 |
| Repaid(6) | 신청 원금 전액 상환 기록 완료 | 소각 | 은행 소유 유지 |

getApplication(appKey)는 borrower, docCid, fileHash, amount, reportCid, reportHash,
appraisedValue, tokenId, repaidAmount, status, evaluator, bank를 반환한다. bank는 Eligible 전까지 영주소다.
SBT와 나중의 NFT는 계약은 다르지만 같은 신청 tokenId를 사용한다.
소각 후 DB의 sbtTokenId는 이력 번호다. 현재 보유 중이라는 뜻이 아니다.

| 함수 | 호출자 | 원자적 처리 |
|---|---|---|
| submitApplication(appKey,cid,fileHash,amount,evaluator) | 차주 | 중복 방지, 평가사 역할 확인(영주소·차주 본인 불가), 신청 기록 + 담당 평가사 고정 + SBT 발급 |
| confirmEvaluation(appKey,reportCid,reportHash,value,bank) | 담당 평가사 | 평가 기록 + SBT 소각 + 자동심사. 통과면 bank의 은행 역할 확인(영주소·평가사·차주 불가) 후 고정, 미달이면 bank는 영주소여야 함 |
| finalApprove(appKey) | 담당 은행 | Eligible만 허용, Approved + 담당 은행에 NFT 발급 |
| finalReject(appKey) | 담당 은행 | Eligible만 허용, Rejected |
| recordRepayment(appKey,amount,paymentRef) | 담당 은행 | Approved만 허용, 중복 참조번호·초과상환 방지, 부분/완납 누적 |

규칙: amount × 100 ≤ appraisedValue × 70. 경계인 70%도 통과한다.
부동소수점이나 화면 LTV 반올림 값으로 계약 결정을 하지 않는다.
금액 단위는 “원” 정수이며 ETH/MST wei가 아니다. 지급·상환 함수에 value를 보내지 않는다.
상환은 원금만 계산한다. paymentRef는 입력한 참조번호의 keccak256 해시이며 신청별 중복을 막는다.
이벤트 Submitted(담당 평가사 포함), EvaluationConfirmed(담당 은행 포함), FinalApproved, FinalRejected, RepaymentRecorded로 변화 이력을 남긴다.
역할 변경은 OpenZeppelin AccessControlEnumerable의 RoleGranted/RoleRevoked로 남고 역할별 주소 목록을 조회할 수 있다.

## 5. 서버·프론트 연결

서버는 web3로 읽기만 한다. 개인키, sign_transaction, send_raw_transaction이 없다.

| API | 기능 |
|---|---|
| GET /api/chain/config | 네트워크, Manager ABI/주소/버전, 토큰 주소, 역할별 등록 주소 |
| POST /api/applications | 암호화 PDF 업로드·DB/프로필 저장, 차주 역할 확인, 담당 평가사 배정 |
| POST /api/applications/{id}/sync | 실제 계약 기록·CID·해시·금액·담당자 주소·토큰 소유권 확인 후 DB 갱신 |
| POST /api/applications/{id}/evaluation-report | 공개 시연 JSON 준비, CID/해시/평가액 반환. 70% 통과 시 담당 은행 배정·반환 |
| POST /api/applications/{id}/document-nonce | 신청·주소에 묶인 5분 일회성 challenge |
| POST /api/applications/{id}/document | personal_sign 검증, 실소유권 확인, 복호화 PDF 응답 |
| PATCH /api/applications/{id} | 온체인 연결 신청은 409로 막음. 기존 화면 시연 예시만 기존 동작 |
| POST /api/reset | 계약 연결 중 409. DB 초기화가 체인을 초기화하지 않기 때문 |

원본 열람: Evaluating의 담당 평가사(SBT 소유자) 또는 Approved/Repaid의 담당 은행(NFT 소유자)만 허용하며, 현재 해당 역할을 보유해야 한다.
Eligible/거절 상태에는 원본 열람권이 없다. 조회 순간 체인 상태를 읽고 nonce는 한 번 사용하면 폐기한다.
서명 메시지는 무료이며, 신청·평가·결정·상환 거래에는 네트워크 가스가 필요하다.

프론트는 지갑 주소·역할·네트워크를 확인하고 staticCall 후 실제 거래를 요청한다.
거래 해시는 브라우저 localStorage에 남긴다. 미확정 거래가 있으면 같은 동작을 재전송하지 않는다.
확정 후 서버 오류는 “체인 확인·복구”로 동기화한다. 이미 완료한 신청은 새 SBT를 만들지 않는다.
브라우저 저장소를 삭제한 채 미확정 거래를 재전송하지 않는다. 자동 이벤트 인덱서·장애 worker는 제외한다.
신청 목록의 초기 8건은 “기존 화면 시연 예시 · 미온체인”이다. 새로 만든 온체인 MVP 신청으로 검증한다.

## 6. 실행·검증 안내

전부 WSL Bash 기준이다. 상세 설치, 실행, 단계별 수동 테스트,
실패 시 확인사항은 [blockchain/README.md](../blockchain/README.md)를 따른다.

검증: Flask 회귀, 프론트/지갑 mock 회귀, 실제 로컬 EVM 계약 테스트,
임시 Flask+SQLite+실제 로컬 EVM 통합 테스트(다중 담당자 배정·우회·회수 포함). 자동 테스트의 IPFS는 mock이며 실제 회사 서버에 업로드하지 않는다.
2026-10-16 검증: 서버 31개 + 프론트 35개 + 계약/통합 19개 = 총 85개 통과.
Mustsem v2 배포 후 실제 MetaMask로 역할 추가, 신청, 평가사 배정, 담당자 원본 열람을 확인했다.
이 검증은 보안 감사를 대신하지 않는다.
