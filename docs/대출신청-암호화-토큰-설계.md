# 대출신청 암호화·토큰 설계 — v3 통합 MVP

수정일: 2026-10-20. 이 문서는 v3 설계와 구현 현황의 기준이다.
v3는 지갑 로그인, 실제 LLM 가치평가보고서, 스마트컨트랙트 대출약정, RWA 토큰을 한 신청 흐름으로 묶는다.
대상 네트워크는 Mustsem(chainId 7601, MST)이다. v3 Manager는 관리자 지갑이 admin.html에서 배포하며, 배포 주소가 정해지면
blockchain/deployments/에 기록하고 서버의 `IPLOAN_MANAGER_ADDRESS`를 바꾼다. 서버는 `contractVersion() == 3`인 계약에만 연결한다.
이전 v2 Manager 0x6D1004CB292e3ec45A4c4A0834C0eedAAbe16E38에 등록된 신청은 DB에 남지만 화면에서 열람만 할 수 있다.
Solidity 0.8.24 + EVM Paris를 유지한다. 실제 자금·법적 채권·담보권을 만들지 않는 시범 구현이다.

## 1. 한 신청의 흐름

1. **지갑 로그인**: 사용자가 MetaMask로 로그인 메시지에 서명한다(거래 아님, 수수료 없음). 서버는 서명을 확인해 세션을 발급하고,
   체인에 등록된 역할(차주·평가사·은행·관리자)로 화면과 API 권한을 정한다.
2. **차주 신청**: 특허등록원부 PDF와 특허 공고전문 PDF를 함께 제출한다. 서버는 원부를 대조(mock)·암호화해 IPFS에 올리고,
   담당 평가사를 배정하고, 공고전문으로 LLM 가치평가보고서 생성을 접수한다.
3. **차주 온체인 등록**: 차주 MetaMask가 `submitApplication`을 실행한다. 신청 기록 + 담당 평가사 고정 + 평가 SBT 발급.
4. **LLM 보고서 생성**: 외부 특허평가 API가 보고서(PDF/HTML)를 만든다. 화면은 10초 간격으로 상태를 확인한다.
5. **평가 확정**: 담당 평가사가 보고서를 검토하고 평가액을 입력한다. 서버가 보고서를 암호화해 IPFS에 등록하고(salted 해시),
   평가가 70% 기준을 통과하면 담당 은행을 배정한다. 평가사 MetaMask가 `confirmEvaluation`을 실행한다.
   보고서 CID·해시·평가액 기록 + SBT 소각 + 70% 자동심사 + (통과 시) 담당 은행 고정이 한 거래다.
6. **대출약정**: 담당 은행 심사역이 신용등급·금리·기간을 정하고 `finalApprove`를 실행한다. 약정 조건이 체인에 기록되고
   은행 지갑에 RWA 토큰이 발급된다. 거절은 `finalReject`.
7. **상환 기록**: 은행이 확인한 상환 내역을 `recordRepayment`로 누적한다. 실제 송금은 없다.

- 신청 자산은 토큰이 아니라 Manager의 신청 기록(struct)이다. 같은 appKey에 평가·약정·상환 상태를 누적한다.
- 신용등급은 심사역이 입력한다. "신용평가 불러오기" 버튼은 서버의 모의 조회(`CC` 반환)를 불러오며, 실제 신용평가 API는 연동 전이다.
- 플랫폼 발급 지갑, 서버 개인키, 서버 자동 거래, 에스크로, 실송금, 이자 계산, 만기·연체, 토큰 매매는 제외한다.
- 평가 확정·최종 결정은 되돌리지 않는다. 재시연은 새 신청으로 한다.

## 2. 역할과 주소

| 역할 | 등록 | 권한 |
|---|---|---|
| 관리자 | DEFAULT_ADMIN_ROLE, v3 배포 지갑 | 차주·평가사·은행 주소 추가·회수(admin.html), 모든 신청 열람 |
| 차주 | BORROWER_ROLE, 여러 주소 | 신청, 본인 신청·약정 열람, LLM 보고서 접수 보완 |
| 평가사 | EVALUATOR_ROLE, 여러 주소. 첫 주소는 생성자에서 등록 | 배정된 신청의 LLM 보고서 검토·평가 확정, 평가 중 원본 열람, 보관 보고서 열람 |
| 은행·여신심사역 | BANK_ROLE, 여러 주소. 첫 주소는 생성자에서 등록 | 배정된 신청의 약정 체결·거절·상환 기록, 승인 후 원본 열람, 보관 보고서 열람 |

배정: 서버가 체인의 역할 보유자 중에서 평가사는 신청 접수 시, 은행은 70% 기준을 통과하는 평가보고서를 준비할 때 고른다.
IPLOAN_ASSIGNMENT_EVALUATOR / IPLOAN_ASSIGNMENT_BANK로 특정 주소를 지정할 수 있고, 비우면 임의 선택한다.
차주 본인은 담당자가 될 수 없고, 평가사는 같은 신청의 은행이 될 수 없다. 서버와 계약 모두 검사한다.
계약은 역할과 신청별 고정만 검증하므로 직접 호출로 다른 등록 주소를 넣는 것은 막지 못한다. 서버의 /sync가 배정 불일치를 거절한다.
기록된 담당자는 바꿀 수 없다. 담당자의 역할을 회수하면 실행·열람이 막히고 해당 신청은 더 진행할 수 없다.
서명 키는 서버에 없으며, 배포·역할 변경을 포함한 MetaMask 승인은 사람이 직접 수행한다.

## 3. 인증·인가

- 로그인: `POST /api/auth/challenge`가 주소·체인 ID·nonce·만료 시각이 담긴 메시지를 만든다(5분, 1회용).
  지갑이 personal_sign으로 서명하면 `POST /api/auth/login`이 서명자를 확인하고 세션 토큰을 발급한다(12시간).
- 챌린지와 세션은 SQLite에 저장한다. gunicorn worker가 여러 개여도 같은 세션을 쓴다. 세션 토큰은 해시로만 저장한다.
- 세션은 "어느 지갑인지"만 증명한다. 역할은 요청마다 체인에서 읽는다(최대 30초 캐시, `IPLOAN_ROLE_CACHE_SECONDS`).
  역할을 회수하면 세션을 지우지 않아도 권한이 사라진다. 원본 열람은 캐시 없이 현재 역할을 다시 확인한다.
- 신청별 권한: 로그인한 지갑이 그 신청의 차주·담당 평가사·담당 은행이어야 한다. 관리자는 모든 신청을 열람한다.
  담당이 아닌 신청은 404로 숨긴다. 보관 보고서는 평가사·은행·관리자만 열람한다.
- MetaMask 계정을 바꾸면 화면이 자동으로 로그아웃한다. 거래는 로그인한 지갑과 같은 계정이어야 전송한다.
- 인증 없는 쓰기 API(PATCH /api/applications/{id}, /api/reset, 원본 열람 nonce)는 제거했다.

## 4. 저장 위치와 공개 정보

### 원부 PDF

1. 프론트가 multipart의 registryDocument 필드로 PDF를 전송한다(최대 20 MiB).
2. 원부 대조를 먼저 수행한다. 현재 verify_registry는 mock이다.
3. 일치하면 파일마다 키 32바이트, salt 32바이트, IV 12바이트를 새로 생성한다.
4. docFileHash = 0x + SHA256(salt || 평문).
5. AES-256-GCM 암호문을 IV(12) || ciphertext || tag(16) 형식으로 만들어 https://api.mustree.kr/upload 에 올린다.
6. CID·해시·신청·기업 프로필을 DB에 저장한다. 키·salt는 SQLite에만 저장하고 공개 API·체인·tokenURI에는 넣지 않는다.

대조 불일치(422)는 doc_verify/hashMatch=0 신청만 저장하고 암호화·업로드·LLM 접수·토큰 발급은 하지 않는다.
IPFS 실패(502/504)는 신청·프로필·공고전문을 저장하지 않는다.

### 특허 공고전문 PDF

patentDocument 필드(최대 50 MiB)로 받는다. 공개 문서이므로 암호화하지 않고 서버 업로드 폴더(`IPLOAN_UPLOAD_DIR`, 0600)에 둔다.
신청 저장 후 같은 신청번호로 외부 특허평가 API에 접수한다. 접수 실패는 신청을 지우지 않고 작업 상태로 남겨 재접수할 수 있다.
접수 결과가 불확실하면(연결 끊김) 중복 접수를 막기 위해 자동 재접수하지 않는다.

### LLM 가치평가보고서

보고서 생성 중에는 서버가 외부 API의 결과물을 담당자에게만 중계한다(HTML은 sandbox 정책).
평가사가 확정하면 서버가 완성된 PDF(없으면 HTML)를 받아 원부와 같은 방식으로 암호화해 IPFS에 등록하고,
reportHash = 0x + SHA256(salt || 보고서) 를 체인에 기록한다. 키·salt·평가 의견은 DB에만 저장한다.
같은 평가액으로 다시 준비하면 기존 등록을 재사용한다. 등록된 보고서 열람은 IPFS 암호문을 복호화한 뒤
체인의 reportHash와 일치할 때만 내려준다.

### 공개 범위와 제한

- 체인에는 차주·담당 평가사·담당 은행 지갑, 원부 CID·salted hash, 신청금액, 보고서 CID·salted hash·평가액,
  약정 신용등급·금리·기간·체결 시각, 상태, 상환 합계가 공개된다.
- RWA 토큰 tokenURI는 위 공개 정보만 담는다. 키·salt·기업 개인정보는 넣지 않는다.
- appKey는 keccak256(신청번호)이며 익명화를 보장하지 않는다.
- 키·salt를 가진 서버 운영자는 원본을 복호화할 수 있다. 종단간 암호화나 운영자 배제 설계는 아니다.
- 원본을 한 번 내려받은 담당자가 복사본을 보관하는 것은 막을 수 없다.

## 5. 계약과 상태

OpenZeppelin 5.0.2, Solidity 0.8.24. IPLoanManager를 배포하면 생성자에서 두 토큰 계약도 생성한다.

| 계약 | 기능 |
|---|---|
| IPLoanManager (v3) | 역할, 신청 struct, 평가·자동심사·대출약정·상환 기록 |
| IPLoanAccessSBT | ERC-721 + ERC-5192 locked. Manager만 발급·소각. 전송·승인 불가 |
| IPLoanRWAToken | 승인된 대출의 RWA 토큰(ERC-721, IPRWA). Manager만 발급. 은행 이후 전송 불가 |

| 상태 | 의미 | SBT | RWA 토큰 |
|---|---|---|---|
| None(0) | IPFS/DB 준비, 아직 온체인 신청 없음 | 없음 | 없음 |
| Evaluating(1) | 차주 등록 완료, 평가 중(은행 미배정) | 담당 평가사 소유 | 없음 |
| Eligible(2) | 평가 확정, 70% 규칙 통과, 담당 은행 고정 | 소각 | 없음 |
| RuleRejected(3) | 평가 확정, 규칙 미통과(은행 없음) | 소각 | 없음 |
| Approved(4) | 은행 약정 체결 | 소각 | 은행 소유 |
| Rejected(5) | 은행 최종 거절 | 소각 | 없음 |
| Repaid(6) | 신청 원금 전액 상환 기록 완료 | 소각 | 은행 소유 유지 |

getApplication(appKey)는 borrower, docCid, fileHash, amount, reportCid, reportHash, appraisedValue, tokenId,
repaidAmount, status, evaluator, bank, creditGrade, rateBps, termMonths, approvedAt을 반환한다.
SBT와 RWA 토큰은 계약은 다르지만 같은 신청 tokenId를 사용한다.

| 함수 | 호출자 | 원자적 처리 |
|---|---|---|
| submitApplication(appKey,cid,fileHash,amount,evaluator) | 차주 | 중복 방지, 평가사 역할 확인(영주소·차주 본인 불가), 신청 기록 + 담당 평가사 고정 + SBT 발급 |
| confirmEvaluation(appKey,reportCid,reportHash,value,bank) | 담당 평가사 | 평가 기록 + SBT 소각 + 자동심사. 통과면 bank 역할 확인 후 고정, 미달이면 bank는 영주소 |
| finalApprove(appKey,creditGrade,rateBps,termMonths) | 담당 은행 | Eligible만 허용, 약정 조건·체결 시각 기록 + Approved + 담당 은행에 RWA 토큰 발급 |
| finalReject(appKey) | 담당 은행 | Eligible만 허용, Rejected |
| recordRepayment(appKey,amount,paymentRef) | 담당 은행 | Approved만 허용, 중복 참조번호·초과상환 방지, 부분/완납 누적 |

규칙: amount × 100 ≤ appraisedValue × 70. 경계인 70%도 통과한다.
약정 조건 검사: 신용등급 1~8자(A-Z, +, -), 금리 1~10000 bps(0.01%~100%), 기간 1~600개월.
금액 단위는 "원" 정수이며 MST wei가 아니다. 지급·상환 함수에 value를 보내지 않는다.
이벤트 Submitted, EvaluationConfirmed, FinalApproved(신용등급·금리·기간 포함), FinalRejected, RepaymentRecorded로 이력을 남긴다.

## 6. 서버 API

서버는 web3로 읽기만 한다. 개인키, sign_transaction, send_raw_transaction이 없다. 아래 표의 로그인 열은 필요한 역할이다.

| API | 로그인 | 기능 |
|---|---|---|
| GET /api/chain/config | 불필요 | 네트워크, Manager ABI/주소/버전, 토큰 주소, 역할별 주소, 최신 블록 |
| POST /api/auth/challenge, /api/auth/login | 불필요 | 지갑 서명 로그인 |
| GET /api/auth/me, POST /api/auth/logout | 로그인 | 현재 지갑·역할, 로그아웃 |
| GET /api/applications | 로그인 | 담당 신청만(관리자는 전체, 보관 보고서는 평가사·은행·관리자) |
| GET·POST /api/borrower-profiles, PATCH /api/borrower-profiles/{id} | 차주 | 이 지갑의 기업 프로필 |
| POST /api/applications | 차주 | 원부 암호화·IPFS, 공고전문 보관, 평가사 배정, LLM 보고서 접수 |
| GET /api/applications/{id}/evaluation | 담당자 | LLM 작업 상태(작업당 10초에 한 번만 외부 조회) |
| POST /api/applications/{id}/evaluation, …/evaluation/identity | 차주·평가사 | 미접수 재접수, 사업자번호 보완 |
| GET /api/applications/{id}/evaluation/artifacts/{kind} | 담당자 | LLM 보고서·근거자료 중계 |
| POST /api/applications/{id}/evaluation-report | 담당 평가사 | 보고서 암호화·IPFS 등록, CID/해시 반환, 통과 시 은행 배정 |
| GET /api/applications/{id}/evaluation-report/document | 담당자 | 등록 보고서 복호화(체인 해시 일치 시) |
| POST /api/applications/{id}/sync | 담당자 | 체인 기록·담당자·토큰 소유권 확인 후 DB 갱신 |
| GET /api/applications/{id}/document | 담당 평가사·은행 | 원부 원본 복호화(평가 중 평가사, 약정 후 은행, 현재 역할 필수) |
| GET /api/applications/{id}/credit-score | 담당 은행 | 모의 신용평가(`CC`). 실제 API 연동 시 교체 |

프론트는 지갑 주소·역할·네트워크를 확인하고 staticCall 후 실제 거래를 요청한다.
거래 해시는 브라우저 localStorage에 남긴다. 미확정 거래가 있으면 같은 동작을 재전송하지 않는다.
확정 후 서버 오류는 "체인 확인·복구"로 동기화한다.

## 7. 기존 데이터 이전

서버 시작 시 한 번씩(반복해도 같은 결과) 다음을 적용한다.

- 지갑·체인 기록이 없는 시드 예시 8건(LN-2026-0088 등)을 삭제한다.
- 기업 프로필은 그 프로필로 마지막에 신청한 지갑의 소유로 정하고, 쓰이지 않는 이전 프로필은 삭제한다.
- 이전 특허평가 화면 DB(`IPLOAN_PATENT_DB_PATH`, 기본 server/patent-iploan.db)의 LLM 보고서 작업을 `archived` 상태로 가져온다.
  보관 건은 열람만 가능하며, 생성 중이던 작업은 상태 조회로 계속 갱신된다. 원본 특허평가 DB 파일은 수정하지 않는다.
- 이전 계약(v2)에 등록된 신청은 `contractOutdated`로 표시되어 열람만 가능하다.

## 9. 검증

전부 WSL Bash 기준이다. 상세 설치·실행·수동 테스트는 [blockchain/README.md](../blockchain/README.md)를 따른다.
2026-10-20 검증: 서버 29개 + 프론트 38개 + 계약·통합 20개 = 총 87개 통과.
추가로 실제 로컬 EVM·임시 API·Chrome에서 테스트 지갑으로 신청→LLM 보고서→평가 확정→신용등급·약정→RWA 토큰→완납 전체 흐름을 확인했다.
자동 테스트의 IPFS·LLM 서비스는 mock이며 실제 회사 서버에 업로드하지 않는다. 이 검증은 보안 감사를 대신하지 않는다.

정식 서비스에서만 검토할 별도 범위: 특허청 원부 실제 대조, 실제 신용평가·TCB, 키 보호/DB 암호화/백업 정책,
API 남용 방어, 이벤트 인덱싱, 재조직·장애 복구, 실금융 및 법적 권리 설계, 보안 감사.
